rusty_zstd — live transfer rates

Real corpora, measured in-process at this moment. Encode and decode are timed separately, best-of-N with a discarded warmup; decode runs into a reused buffer. Checksum is off on both arms so the C comparison is like-for-like.
Idle. Press Run.
R is us, C is zstd v1.5.7. Each phase shows both arms and the ratio between them: R/C enc and R/C dec are our MB/s ÷ C's MB/s, so above 1.00× we are faster (green) and below it we are slower (red). Careful when cross-checking against m7-anatomy.md — that page prints the inverse, C/us, where above 1.00 means C is faster.

R/C size is our output bytes ÷ C's output bytes — who emits the smaller file. Below 1.000 we win. It is the only column here that is fully deterministic: it carries no spread and does not move between runs at any cap. Hover it for the underlying byte counts and for how much the file actually shrank (1.00× or “grew” means the data was incompressible — every codec adds a small header to data it cannot compress, so random input always ends up slightly larger than it started, for us and for C alike).

Read the ± beside every rate. It is a same-arm spread from two independent best-of-N arms on identical input; amber above 10%, red above 25%. When it is large the rate cannot separate small differences — a 1 MiB cap is usually the cause, so raise the cap or the iteration count. Compressed sizes are deterministic and carry no such caveat at any cap.
